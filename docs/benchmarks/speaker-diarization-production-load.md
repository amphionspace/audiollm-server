# Streaming Sortformer 同卡生产压测报告

日期：2026-08-05

更新结论：初始逐会话串行推理在 16 路有 11/16 会话因角色结果超时而 fail-open。
加入单卡动态 batching（batch 8、等待 12 ms）后，同一 16 路测试为全量角色、
零降级，直接角色 watermark wait p95 从 1.236 秒降到 0.786 秒。角色功能稳定容量
已验证到 **16 路**；但完整 AST final lag p95 为 2.378 秒。如果生产要求完整终稿
p95 严格低于 2 秒，仍按 **8 路低时延水位**规划，12 路为边界观察位。

## 1. 测试目标与门禁

本轮验证生产配置下 `/tuling/ast/v3`、ASR 与 diarization sidecar 同卡运行时的：

- 普通 ASR 与角色分离 A/B 性能回归；
- 角色结果等待、超时降级和过载恢复；
- GPU 峰值、OOM 与 systemd 进程稳定性；
- 可作为生产容量下界的同相位并发水位。

发布门禁为：无 OOM、至少保留 10 GiB 显存、角色等待 p95 小于 2 秒、稳定档位
现有 ASR TTFT p95 回归不超过 5%。角色能力发生 fail-open 的档位不计入“性能回归
通过”，因为其低时延可能来自角色功能已被关闭。

## 2. 环境与方法

| 项目 | 值 |
| ---- | ---- |
| 服务 | `audiollm-demo.service` + `audiollm-diarization.service` |
| 端点 | `ws://127.0.0.1:8082/tuling/ast/v3`，同机回环 |
| diarization 模型 | `nvidia/diar_streaming_sortformer_4spk-v2.1` |
| 数据 | AliMeeting Test far，`R8002_M8002` 前 30 秒 |
| 音频格式 | 16 kHz、mono、PCM S16LE |
| 推流方式 | realtime，80 ms PCM 包，同一音频复制 N 路并同相位起跑 |
| A/B 开关 | baseline 显式传 `enable_role_separation=false`；role 显式传 `true` |
| 脚本 | `scripts/bench_tuling_ttft.py` |

同相位起跑会让多路会话在相近时间切段、等待角色结果并请求 ASR，是偏保守的
worst-case 容量口径。每个档位只运行一批同源音频，结果用于当前机器容量定界，
不代表真实业务流量的统计分布。

## 4. 12 路补测与角色等待

12 路只运行角色分离路径，12/12 ASR 成功且没有角色降级；有效吞吐为 10.877x，
TTFT p95 为 11.794 秒，但 final lag p95 为 2.381 秒。它证明角色功能在 12 路仍可
维持，却已经越过 2 秒用户可见尾部目标，不宜作为默认生产水位。

为分离 sidecar 自身耗时与完整 AST/ASR 链路争用，又对 15 秒音频执行了直接 gRPC
等待测试。每路在 10、12、15 秒 watermark 处取一次结果：

| 并发 | 测量数 | wait p50 | wait p95 | wait p99 | max | 降级 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 1 | 3 | 670 ms | 754 ms | 762 ms | 764 ms | 0 |
| 4 | 12 | 713 ms | 810 ms | 822 ms | 825 ms | 0 |
| 8 | 24 | 749 ms | 910 ms | 937 ms | 943 ms | 0 |
| 16 | 48 | 976 ms | 1,236 ms | 1,285 ms | 1,297 ms | 0 |

sidecar 单独运行到 16 路仍没有超时，而完整 AST v3 16 路出现 11 次
`result_timeout`。结合 GPU 利用率已到 99%，证据指向同卡完整链路的调度/资源争用
和固定 2 秒结果期限，而不是显存不足或 sidecar 单独推理能力不足。该判断是基于本轮
对照的工程归因；如需把安全水位提高到 12 路以上，还应补充 GPU kernel、事件循环和
ASR 请求队列的分项 tracing。

优化前生产建议：

- 当前单 H20 按 **8 路同时开启角色分离的 AST v3 会话**规划；这是同相位
  worst-case 的安全水位，不等同于所有 ASR 接口的总并发上限。
- 12 路可作为告警/扩容观察位，不能当默认承诺容量；其角色虽稳定，但尾部 p95 已

  `diarization_result_timeout_sec` 掩盖争用。

## 8. 单卡动态 batching 优化复测

### 8.1 根因与改动

初始 sidecar 为每条流创建 `batch_size=1` state，所有 `process_signal` 和
`forward_streaming_step` 又经过同一个模型锁。16 条同相位流每 480 ms 形成一批串行
任务；同时，角色重切把该批 16 路的 final sentence 数从普通 ASR 的 57 提高到完整
角色路径的 175。GPU 计算达到 99% 后，11 条流的 watermark 等待越过固定 2 秒期限。

优化保持一个模型实例和一张 H20，不增加依赖，也不修改客户端协议、角色阈值或 2 秒
fail-open 契约：

- sidecar 最多等待 12 ms 收集同相位请求；
- 只合并窗口长度、offset 和所有 speaker-cache tensor 形状完全相同的请求；
- NeMo batched state 推理后，把每项 state clone 回对应会话，避免跨会话共享 storage；
- 默认 batch 上限为 8。batch 16 作为对照运行，但没有作为生产值。

真实 GPU 等价性测试使用 AliMeeting `R8002_M8002_MS802` 前 30 秒，先单路完整推进，
再把相同 PCM 以两路 batch 推进；两路的全部 `ModelUpdate`（watermark、turn 起止与
speaker index）均与单路逐项相等。该窗口超过 speaker-cache 更新周期，覆盖了 cache
压缩后的状态拆分，而不只是短静音接线测试。

### 8.2 优化后结果

| 并发/配置 | ASR 成功 | 角色稳定 | TTFT p95 | final lag p95 | 有效吞吐 | 说明 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 1 / batch 8 | 1/1 | 1/1 | 13.710 s | 0.460 s | 0.977x | 单路 smoke |
| 8 / batch 8 | 8/8 | 8/8 | 13.986 s | 1.188 s | 7.527x | 比优化前 1.578 s 降低 24.7% |
| 12 / batch 8 | 12/12 | 12/12 | 14.158 s | 2.020 s | 10.997x | 零降级，完整尾部处于 2 秒边界 |
| 16 / batch 8 | 16/16 | 16/16 | 12.530 s* | 2.378 s | 14.463x | 优化前仅 5/16 保留角色 |
| 16 / batch 16 | 16/16 | 16/16 | 13.994 s* | 2.436 s | 14.438x | kernel 更长，未采用 |
| 16 / 普通 ASR | 16/16 | 不适用 | 13.727 s* | 1.416 s | 14.867x | 同阶段 A/B baseline |

\* 高并发中存在前导静音误识别，TTFT 绝对值不能作为质量无损指标。batch 8 的 16 路
吞吐相对同时期普通 ASR 回归 2.715%；角色路径需要输出 175 个 final，而普通路径为
57 个，因此完整 final lag 差异同时包含角色拆段后必须执行的额外 ASR 工作。

直接 gRPC 测试继续发送 PCM，并记录 watermark 越过 10、12、15 秒边界相对对应 PCM
已发送时刻的等待。16 路共 48 个测量：优化后 p50 698 ms、p95 786 ms、p99 786 ms、
最大 786 ms；优化前 p95 为 1,236 ms、最大 1,297 ms。该结果证明 diarization 等待
本身已明显低于 2 秒；完整 AST 的 2.378 秒尾部主要在角色拆段后的 ASR 收尾。

batch 8 的 16 路 GPU 峰值 used 为 51,574 MiB，最低 free 为 45,794 MiB，峰值利用率
100%；无 OOM、无服务重启。batch 16 峰值 used 为 51,768 MiB，最低 free 为
45,600 MiB，也没有内存压力，但 final lag 更高，说明扩大 batch 不能只看 GPU
吞吐，还必须考虑同卡 ASR 公平性。全部上探和最终恢复到生产 batch 8 后，单路 AST
复测 1/1 成功、无角色降级，final lag 为 455 ms。

### 8.3 当前单卡容量结论

- **角色功能容量：16 路已实测稳定**，16/16 保留角色，无 `result_timeout`。
- **完整终稿低时延水位：8 路**，final lag p95 为 1.188 秒；12 路为 2.020 秒边界，
  16 路为 2.378 秒。
- 生产使用 batch 8 / 12 ms。继续提高单 batch 不增加可用容量，反而轻微伤害 ASR
  尾部；若还要压低 16 路终稿，需要优化角色拆段后的 ASR/热词召回批处理，而不是
  放宽 diarization timeout。
